DPVS 负载均衡与长连接排查指南

发表于 2026-11-27 阅读次数：
本文字数： 9.6k 阅读时长 ≈ 9 分钟

适用场景：Kubernetes Pod 作为 Real Server（RS），前置四层 VIP，DPVS 承载 TCP 长连接；本文以 VIP=10.242.11.184:8000、旧 Pod RS=10.243.190.71:8000 为示例。

重要说明：DPVS 的命令名称、配置项和下线语义可能因公司封装版本、控制器和数据面实现而不同。本文给出通用原理和排查框架；涉及“RS 下线后保留已有连接”的行为，必须以司内 DPVS 版本、控制器日志和实际连接表为准。

1. 结论摘要

  1. RS 下线不等于已有连接一定断开。 理想的连接排空语义是：RS 不再接收新连接，但已经建立的连接继续由连接表转发，直到连接自然结束或达到 TCP 超时。
  2. 这个能力通常依赖两个条件：
    • 控制器执行的是“置零/Drain”，而不是立即删除 RS、删除虚拟服务或清理连接表；
    • DPVS 数据面在 RS 下线后仍保留已有连接对应的连接状态和转发路径。
  3. fullnat 不是连接保持开关。 FullNAT 主要描述报文的地址转换方式；连接能否保持取决于 RS 下线动作、连接表处理、超时、健康检查和链路设备行为。
  4. 当前问题最应确认：
    • 35 秒时控制器究竟执行了 weight=0、drain、inhibit，还是删除 RS；
    • DPVS 的已有连接表是否仍存在；
    • fullnat 下前端连接和后端连接是否被同时关闭；
    • 断开是 FIN/RST，还是连接状态被清理后重传超时。

2. “下线 RS 后连接保持”到底是什么

2.1 三种常见下线语义

方式 新连接 已有连接 风险
权重置 0 不再或尽量不再调度到该 RS 通常保留 需要确认调度器是否只影响新连接；权重为 0 的精确定义要看实现
Drain/Inhibit 不接新连接，等待连接自然结束 保留到结束或超时 需要配置排空超时、连接上限和兜底强杀
删除 RS/清理连接 不接新连接 可能立即断开 发布快，但不适合长连接

2.2 FullNAT 下的连接模型

FullNAT 通常对客户端到 VIP、VIP 到 RS 两个方向都做地址转换。逻辑上可以理解为两段连接：

DPVS 通过连接状态把两段流量关联起来。RS 下线后能否继续转发，取决于：

  • 前端连接状态是否保留；
  • 后端连接状态是否保留；
  • FullNAT 使用的 SNAT 地址/端口是否仍有效；
  • RS、Pod 网络、节点 conntrack 或中间设备是否接受后续报文；
  • 控制器是否在下线时主动删除连接表；
  • TCP 连接空闲超时、FIN 超时、TIME_WAIT 超时是否足够长。

因此，“fullnat 支持连接保持”更准确的表述应是：FullNAT 具备实现连接保持所需的状态转换能力，但实际是否保持由下线流程和数据面策略决定。

3. 常见四层转发模式对比

术语在不同 LB 产品中可能略有差异。下表按 LVS/DPVS 常见语义整理。

模式 请求方向 响应方向 是否需要 RS 配置 VIP 性能 长连接排空 典型限制
NAT/FullNAT LB 改写目的地址；FullNAT 同时改写源地址 LB 改写回包 通常不需要 中等，需处理双向转换 能否保持取决于连接表和下线策略 LB 需要承载双向流量；SNAT 端口、连接表、带宽是瓶颈
DR（Direct Routing） LB 改写二层目的 MAC，IP 基本不变 RS 直接回客户端 通常需要 RS loopback 配 VIP，并抑制 ARP 很高，响应不经过 LB RS 下线时需确保连接继续由 RS 回包 二层网络约束强；跨网段、云网络、Pod 网络常较复杂
TUN/IPIP LB 封装 IP 包发给 RS RS 直接回客户端 通常需要配置 VIP 高，响应不经过 LB 依赖隧道和 RS 配置 需要隧道、MTU、路由及协议支持
FullNAT + 代理/网关扩展 LB 或代理维护更完整会话 通常经 LB 返回 一般不需要 取决于实现 可做更明确的 drain 资源消耗更高，连接语义可能不是纯四层

3.1 FullNAT/NAT

优点：

  • RS 不需要感知 VIP，适合 Pod、跨网段和复杂云网络；
  • 客户端源地址可被转换，回程不要求经过原始网络路径；
  • 易于统一管理、做连接状态和访问控制。

缺点：

  • 请求和响应都经过 LB，带宽、CPU、内存和连接表压力更高；
  • 需要重点关注 SNAT 地址池、临时端口耗尽、连接表容量和超时；
  • 数据面或连接表清理时，已有长连接可能同时受到影响。

3.2 DR

优点：响应直接从 RS 返回，吞吐和时延通常更好，LB 主要承担入方向流量。

缺点：RS 必须正确配置 VIP、ARP 抑制和路由；在 Kubernetes、跨三层网络、Overlay 网络中，部署和排障复杂度通常高于 FullNAT。

3.3 TUN

优点：相比 DR 对二层网络要求较低，响应绕过 LB。

缺点：需要隧道封装、额外 MTU 规划、RS 路由和内核能力；封装异常时容易出现分片、PMTU 和回程问题。

4. DPVS 原理

DPVS（通常指 DPDK-based LVS）把 LVS/IPVS 的负载均衡模型与 DPDK 用户态高速收发包结合起来。典型处理路径如下：

关键特点：

  • 使用 DPDK 用户态 PMD，绕过传统内核网络栈的部分路径；
  • 连接调度通常只发生在新连接，已有连接依赖连接表保持原后端；
  • 多核、RSS、队列和连接表设计直接影响性能；
  • 控制面负责同步 VIP、RS、权重、健康状态和下线动作；
  • 高可用通常由 Keepalived、VRRP、专有控制器或集群管理系统负责。

5. 推荐的 DPVS 集群架构

5.1 双机 Active/Standby

特点：实现简单，VIP 同时只在一台设备上提供服务；切换时需要考虑连接状态同步，否则已有连接可能重建或断开。

5.2 双机 Active/Active 或 ECMP

特点：吞吐和容量更高，但要求上游流量分担、连接一致性、健康检查、配置分发和故障切换设计成熟。FullNAT 场景尤其需要确认同一连接的前后方向始终落到可查到该连接状态的节点，或者使用连接状态同步/确定性流量归属。

5.3 集群必须关注的组件

  1. 数据面节点：DPVS 进程、DPDK、网卡队列、NUMA、CPU 绑核。
  2. 控制面：VIP/RS 配置下发、权重调整、健康检查、Drain、发布联动。
  3. 高可用：VRRP/Keepalived、BFD、ECMP 或司内 HA 组件。
  4. 状态同步：连接表同步、配置同步、版本一致性和切换恢复策略。
  5. 观测系统：连接数、新建连接、转发包、丢包、重传、RST、RS 状态和下线耗时。

6. DPVS 重点参数与检查项

以下是排查长连接和 RS 下线问题时优先确认的项目。

6.1 VIP/RS 与调度

  • VIP、端口、协议是否正确；
  • RS 的权重变化是否只影响新连接；
  • 权重为 0 是否保留已有连接；
  • 是否存在 inhibit、drain、quiesce、delay 等司内扩展语义；
  • 健康检查失败是否会立即删除 RS 或清理连接；
  • 调度算法是 rr、wrr、lc、wlc、sh、dh 还是定制算法；
  • 发布时是否同时删除了旧 RS、旧虚拟服务或对应的连接表。

6.2 TCP 连接超时

至少核对以下几类超时，单位和参数名以当前版本为准：

  • TCP established 超时；
  • TCP close/FIN_WAIT 超时；
  • TCP TIME_WAIT 超时；
  • SYN/SYN-ACK 建连超时；
  • UDP 超时（如有 UDP 服务）；
  • 空闲连接超时；
  • RS drain 最大等待时间；
  • 控制器下线等待时间；
  • 云网络、节点 conntrack、防火墙和上游设备的空闲超时。

对长连接而言，最重要的是：业务心跳间隔必须显著小于链路上最小空闲超时。否则连接可能看起来“随机断开”。

6.3 FullNAT 资源

  • SNAT 地址池大小；
  • 每个 SNAT 地址可用临时端口范围；
  • 单 VIP、单 RS、单 DPVS 节点连接数；
  • 连接表容量和内存使用；
  • 端口冲突、端口耗尽、连接创建失败计数；
  • FullNAT 地址池是否跨节点一致；
  • 回程报文是否一定回到正确 DPVS 节点；
  • 是否存在内核 conntrack 与用户态连接表双重状态不一致。

6.4 DPDK/网卡/CPU

  • 网卡 RX/TX 队列数和 RSS 配置；
  • lcore 绑核、NUMA 与网卡所在 NUMA 节点是否匹配；
  • RX/TX ring、mbuf、内存池是否耗尽；
  • 丢包、网卡错误、队列溢出和突发流量；
  • jumbo frame、MTU、VXLAN/隧道封装后的有效 MTU；
  • 多队列 RSS 是否导致同一连接前后方向分散到不兼容的核或节点；
  • DPDK、网卡固件和 DPVS 版本是否匹配。

6.5 下线与连接排空

要求运维明确回答以下问题：

  1. RS 下线动作的 API/命令是什么？
  2. 下线后 RS 是否仍出现在连接表中？
  3. 连接表是否会因 RS 删除而被批量清理？
  4. 已建立连接上的数据包是否仍允许转发到 weight=0 的 RS？
  5. Drain 的最大等待时间是多少？超时后是 FIN、RST 还是直接丢包？
  6. 下线时是否同步删除 ARP、路由、NAT 地址或 SNAT 端口映射？
  7. DPVS 是否把客户端和 RS 侧连接分别记录，并提供关闭原因？

7.1 建立 VIP 和 Pod 直连对照

注意：该测试验证的是 HTTP keep-alive。若真实业务是 WebSocket、SSE、gRPC 或自定义 TCP 协议，应使用真实协议建立连接；测试客户端不要自动重连，否则可能误把新 Pod 的连接当作旧连接仍然正常。

7.2 在旧 Pod 或节点抓包

如果权限和网络环境允许，建议同时在以下位置抓包：

  1. 客户端侧：观察 VIP 连接收到 FIN、RST，还是只发生重传；
  2. DPVS 入方向：观察客户端到 VIP 的报文是否仍到达；
  3. DPVS 出方向：观察 DPVS 到 Pod 的报文是否仍发送；
  4. Pod 侧：判断 Pod 是否主动发送 FIN/RST；
  5. DPVS 连接表：确认连接是否仍存在以及关闭原因。

7.3 用时间线判定因果

至少记录以下时间点，精度建议到毫秒：

判定参考：

  • T4≈T2，Pod 没有先发 FIN/RST，且 DPVS 连接表被删除：优先认定为 LB 下线/清理导致；
  • DPVS 连接表仍在，但 DPVS 到 Pod 不再发包：检查 RS 下线策略、转发表和 FullNAT 后端状态；
  • Pod 先发 FIN/RST：查 preStop、应用 drain 逻辑和应用日志；
  • 只有重传、没有 FIN/RST，最终超时：查 DPVS 状态清理、网络 ACL、节点转发和丢包；
  • VIP 连接断、Pod 直连不断：问题集中在 LB 或 LB 独有路径；
  • VIP 与 Pod 直连同时断：优先查应用、Pod 网络、节点或发布流程。

8. 常用维护与排障命令

命令可能需要 root 权限；部分 DPVS 发行版把命令放在 /usr/local/bin、/usr/bin 或专用管理容器中。先执行 command -v 和 --help，不要直接假设参数完全兼容。

8.1 IPVS/DPVS 服务与 RS

常见关注字段：VIP:Port、RS 地址、Forwarding 模式、Weight、ActiveConn、InActConn、Packets、Bytes、连接创建失败和丢包统计。

ipvsadm 在某些 DPVS 版本中可用于查看或管理兼容的 IPVS 配置，但不是所有 DPVS 专属能力都一定通过它暴露。若输出为空或与控制器状态不一致，应使用司内 DPVS CLI/API 和控制器侧查询结果交叉确认。

8.2 Linux 网络与连接

FullNAT/DPDK 数据面可能绕过部分内核统计，因此 ss、conntrack 的结果不一定等于 DPVS 真实连接表；它们适合用于发现节点侧辅助状态和异常，不应作为唯一证据。

8.3 抓包和连接行为

若 DPVS 使用独占 DPDK 网卡，Linux tcpdump 可能抓不到数据面报文，此时需要使用 DPVS/DPDK 自带抓包、端口镜像、硬件镜像或在客户端/RS 侧抓包。

9. 建议向运维确认的具体问题

可以直接把下面的问题发给 DPVS/LB 运维：

  1. 司内所谓的 fullnet/fullnat 的准确产品名和版本是什么？是否是 FullNAT？
  2. RS 下线 API 的实际动作是 weight=0、inhibit/drain 还是 delete RS？
  3. RS 下线后，已有连接是否继续查连接表并转发？是否有官方说明或测试结果？
  4. “连接保持”配置的准确名称、作用范围和默认值是什么？是 TCP established timeout、drain timeout，还是连接表保留开关？
  5. 连接保持的最大时长是多少？空闲连接和有心跳连接是否不同？
  6. RS 下线时是否会批量删除连接表？能否查询下线前后的连接数？
  7. DPVS 是否发送 FIN/RST，还是删除映射后让连接超时？
  8. FullNAT 的 SNAT 地址池、临时端口范围和连接表容量是多少？
  9. DPVS 集群是否做连接状态同步？主备切换后已有 FullNAT 连接能否继续？
  10. 35 秒是控制器等待时间、配置生效时间，还是数据面开始 drain 的时间？能否提供 T1/T2 的日志时间戳？

对于有长连接的 Pod，建议把发布流程设计成显式的多阶段流程：

配套要求：

  • preStop 中打印开始、下线完成、连接数、退出原因和时间戳；
  • 应用支持优雅关闭，区分“停止接新连接”和“关闭已有连接”；
  • LB 控制器提供可观测的操作 ID 和数据面确认状态；
  • terminationGracePeriodSeconds 应覆盖“控制面传播 + drain 最大等待 + 应用退出”总时间；
  • 不要仅凭 preStop 仍在运行，就认为 VIP 到旧 Pod 的连接一定会被保留。

11. 一句话定位原则

先确认 DPVS 的实际下线动作，再确认连接表是否保留，最后用客户端、DPVS、Pod 三点抓包对齐 FIN/RST/重传时间。 只要能证明“DPVS 实际摘除或清理连接发生在客户端断开之前，且 Pod 没有主动关闭”，就可以把问题从 Kubernetes 优雅终止进一步收敛到 LB 的下线/连接保持实现。
