ipvsadm 命令与 Kubernetes IPVS 排障

发表于 2026-01-08 更新于 2026-09-08 阅读次数：
本文字数： 6.9k 阅读时长 ≈ 6 分钟

本文解释下面这条命令的含义，并整理 Kubernetes 使用 kube-proxy IPVS 模式时的常用查看和排障方法：

1. 这条命令做了什么

参数说明：

参数 含义
-l / --list 列出当前 IPVS 虚拟服务和后端 Real Server
-n / --numeric 直接显示数字 IP 和端口，不做 DNS 反向解析
--rate 显示速率相关统计；具体列和版本有关
--stats 显示连接、包和字节统计
--exact 精确显示计数值，不使用 K/M/G 等人类可读缩写
grep 172.24.0.2 在命令输出中筛选这个 IP；它不是 ipvsadm 的过滤条件

这条命令查询的是当前执行节点的本机 IPVS 表，不是直接查询 Kubernetes API。只有当该节点使用 kube-proxy 的 IPVS 模式时，才能通过它观察 Kubernetes Service 的本地代理规则。

2.1 为什么要以表头为准

--rate 和 --stats 的显示方式、列顺序、是否同时展示，可能随 ipvsadm 版本变化。你使用 grep 后，原始表头被过滤掉了，所以看不出数字到底对应哪一列。--stats 通常是累计值，--rate 才是当前速率值；二者不能混为一谈。

6. 常见异常与判断方法

6.1 Service 存在，但 IPVS 没有对应 VIP

可能原因：

  • 当前节点 kube-proxy 没有运行或不在 IPVS 模式。
  • kube-proxy 无法 watch API Server。
  • IPVS 内核模块未加载，或 ipvsadm/内核能力不匹配。
  • kube-proxy 配置修改后没有生效。
  • 你查看的不是实际承载流量的节点。
  • Service 使用了不同的 IP family 或 dual-stack 地址。

6.2 VIP 存在，但没有后端 Real Server

可能原因：

  • Service selector 没有匹配 Pod。
  • Pod 没有 Ready，EndpointSlice 中 ready=false。
  • targetPort 与容器监听端口不一致。
  • EndpointSlice 尚未同步到 kube-proxy。
  • Service 使用了手工 Endpoints，但地址不可用。

计数器增长说明匹配到流量，不等于服务健康。还要区分：

  • 连接/包是否有对应的出方向增长。
  • 后端 Real Server 是否均匀收到流量。
  • 是否存在大量 UDP 短流量或 DNS 重试。
  • 是否出现单个后端异常、超时或丢包。

7. 最佳实践

  • 先确认 kube-proxy 模式，再使用 ipvsadm；iptables 模式下主要检查 iptables-save，Cilium eBPF 模式下不能把 IPVS 当作主数据面。
  • 保留未经过滤的原始输出，避免 grep 把表头过滤掉，导致误解字段。
  • 用 -n 避免反向 DNS 解析影响排查速度。
  • 使用 --exact 保留精确计数，做前后差值时不要使用缩写值。
  • 长期观测使用指标系统，不要用高频 ipvsadm 轮询替代监控。
  • 一定同时检查 Kubernetes API 中的 Service、EndpointSlice 和 Pod Ready 状态。
  • 不要直接用 ipvsadm 手动删除或修改 kube-proxy 管理的 Service 规则；kube-proxy 会重新同步，手工修改可能造成短暂抖动和状态不一致。
  • 不要把 ipvsadm -C 当作“修复命令”。它会清空本机 IPVS 表，可能导致节点所有 Service 流量中断。
  • 不要仅凭 VIP 有计数判断后端健康；必须检查 Real Server、应用监听和端到端请求。
  • 修改 kube-proxy、内核模块、IPVS 调度算法或连接超时前，先在单节点/测试环境验证。
  • UDP 服务需要特别关注超时和 conntrack；DNS 业务同时检查 UDP 53、TCP 53 和应用重试。
  • 多网卡节点要确认 kube-proxy 使用的 node IP、Pod 路由和返回路径。
