背景

RKE2 是 Rancher Kubernetes Engine 2，设计上更接近标准发行版 Kubernetes。

核心特点：

  • 单个 rke2 二进制。
  • systemd 管理 RKE2 服务。
  • 自带 containerd，不依赖 Docker。
  • 自带 Kubernetes 组件。
  • 默认使用静态 Pod 和 RKE2 内置控制逻辑。
  • Server 节点默认运行控制面和 embedded etcd。
  • Agent 节点只运行 worker 相关组件。
  • 通过配置文件和 token 加入集群。
  • 使用 /etc/rancher/rke2/config.yaml 配置。
  • 使用 /etc/rancher/rke2/registries.yaml 配置镜像仓库。
  • 使用 kubeconfig 和标准 kubectl 管理集群。

部署前风险检查

  1. 版本真实性：确认目标 RKE2、Helm、cert-manager、Rancher 版本在目标环境可获取且相互兼容。
  2. cgroup v2：修改内核启动参数前确认操作系统、grubby 行为和回滚方式；重启属于高风险操作。
  3. 镜像源：镜像代理可用性、证书和内容一致性需要验证。
  4. RKE2 端口：确认 9345、6443、2379、2380 及其他实际所需端口的网络策略。
  5. etcd 高可用：Server 数量应为奇数，并验证 etcd 成员健康、时钟同步和磁盘性能。
  6. 敏感信息：token、bootstrap password、配置文件中的凭据不得进入 Markdown 或聊天记录。
  7. crictl 路径：RKE2 与 K3s 的运行时 socket 路径可能不同，不能直接照抄。
  8. Rancher 初始密码：不要使用命令行明文参数或文档明文记录，应使用 Secret 管理。
  9. 回滚方案：对内核参数、RKE2 服务、Rancher Helm release 和 CRD 分别准备回滚步骤。
  10. 验证标准：不能只看 systemd active/activating，还要结合节点 Ready、Pod 状态、etcd 健康、API 可用性和 Rancher /ping 验证。

Dense vs MoE

  • 模型容量 ≈ 总参数（决定知识储量）
  • 推理算力 ≈ 激活参数（决定计算量）
  • 结论：MoE 让你用”小模型的推理成本”换”大模型的知识储量”
视角 Dense 70B MoE 671B/A37B
推理算力 高（全参数过一遍） 低（只激活 37B）
推理显存 中（140 GB FP16） 高（1.3 TB FP16，要装全部专家）
部署门槛 中（2 张 H100 够用） 高（需要 8+ H100 集群）
训练复杂度 低 高（路由算法、专家负载均衡）

Prefill vs Decode

阶段 计算特性 主要瓶颈
Prefill 一次处理 n 个 token，并行度高 算力（compute-bound）
Decode 一次处理 1 个 token，串行生成 显存带宽（memory-bound）
  • Decode 阶段：每生成 1 个 token，都要把整个模型权重从 HBM 读到 SRAM 一遍。
  • 投机解码的切入点： GPU 99% 的算力在 decode 时被浪费了。Tokenizer 必须完全一致——同家族模型才行（Llama → Llama，不能 Llama → Qwen）
  • 投机解码最大的反直觉事实：batch 越大，投机解码的收益越小。投机解码利用的是”闲置算力”，大 batch 已经把算力打满。

背景信息

向量数据库：为什么在 AI 时代它是“必需品”？

背景：传统数据库的“死穴”

过去我们用 MySQL、PostgreSQL，核心是“关键词匹配”。

  • 比如搜索“快乐”，数据库会查找包含“快乐”这两个字的记录。
  • 缺陷： 如果记录里写的是“开心”或者“愉悦”，传统数据库就搜不到。它不懂语义，只懂字符。

产生：AI 语义理解的爆发

随着深度学习（特别是 Transformer 模型）的出现，我们发现可以把任何东西（文本、图片、声音）映射成一个“语义向量”。

  • 在向量空间里，“快乐”、“开心”、“愉悦”的坐标挨得很近。
  • 向量数据库诞生了： 为了解决这种“高维空间下的海量数据相似度搜索”问题，专门优化的数据库应运而生。

核心作用：AI 的“长期记忆”

大模型（如 Qwen）本身有知识截止日期，且不能存储海量的用户私人数据。

  • 作为 AI 的外挂大脑： 向量数据库存储了企业私有文档、代码库、历史对话。
  • RAG (Retrieval Augmented Generation)： 这是目前最主流的应用场景。用户提问时，系统去向量库找相关的知识片段，再把知识片段塞给模型。
  • 总结： 大模型负责“逻辑推理”，向量数据库负责“提供事实”。

核心价值：

  1. 突破模型遗忘： 让模型可以随时访问最新、最私密的数据。
  2. 极速搜索： 在亿级向量数据中，通过索引技术（如 HNSW 算法），在几毫秒内找到语义最相关的结果，这是传统数据库遍历全表无法做到的。
  3. 多模态桥梁： 不管是图片还是文字，到了向量库里都是“坐标”。这让你可以实现“以图搜图”、“文字搜图片”等跨模态操作。
